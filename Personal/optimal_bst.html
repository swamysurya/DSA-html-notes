🌲 Optimal Binary Search Tree (OBST) Digital Lecture Notes

1. What is a Binary Search Tree (BST) & Why Use It?

Page 1

When we have a collection of keys and want to search for elements, we have traditional search techniques such as linear search and binary search. We also have a hierarchical data structure called a Binary Tree. Can we utilize a binary tree for searching purposes? Yes! By organizing the keys such that every node satisfies the ordering invariant, we form a Binary Search Tree (BST).

Arranging Keys as a Binary Search Tree

Suppose we are given 7 keys: 10, 20, 30, 40, 50, 60, 70. We arrange them into a binary tree with 40 as root, 20 as left child, and 60 as right child:

🌿 Root: 40  |  Left: 20 (with children 10, 30)  |  Right: 60 (with children 50, 70) Height: h = log₂(7) ≈ 3 • Max Comparisons = 3

🔑 The BST Property:

For any node in the tree:

  • All elements on its left-hand side are smaller.
  • All elements on its right-hand side are larger.
  • For node 40: elements {10, 20, 30} are smaller (left), and {50, 60, 70} are larger (right).
  • For node 60: 50 is smaller (left), and 70 is larger (right).

Searching a Key in this BST (Successful vs Unsuccessful)

Case 1: Successful Search

Search for Key: 50

  1. Start at root 40. Is it 50? No, 50 > 40 → definitely on right hand side.
  2. Move to 60. Is it 50? No, 50 < 60 → go to left hand side.
  3. Move to 50. Is it 50? Yes! Key found!

Total comparisons = 3 (= Level of node 50).

Case 2: Unsuccessful Search

Search for Key: 45

  1. Start at root 40: 45 > 40 → go right to 60.
  2. At 60: 45 < 60 → go left to 50.
  3. At 50: 45 < 50 → go left of 50.
  4. Left child of 50 is null! Search terminates → Unsuccessful!

Search terminates at leaf level. Search may be successful or unsuccessful.

⏱️ Time Complexity for Searching in a BST:

The maximum time taken for searching a key element will occur if the element is in the leaf. The number of comparisons required equals the height of the tree.

Height of a balanced binary tree is minimum: h = log₂(n) ⇒ Time Complexity = O(log n).

How Many Different BSTs are Possible for n Keys?

For any given collection of n keys, the total number of distinct Binary Search Trees that can be formed is given by the Catalan Number formula:

⇒ Exactly 5 different binary search trees are possible for 3 keys! For any n keys, 2nCn / (n + 1) trees are possible.

Part A: Cost Calculation when All Keys Have Equal Frequency

What is the cost of searching in each tree? The search cost depends directly on the number of comparisons required to reach each key element:

• Searching key at Level 1 (Root): 1 comparison
• Searching key at Level 2: 2 comparisons
• Searching key at Level 3: 3 comparisons
When all 3 keys are searched with equal frequency, the efficiency is given by the average number of comparisons = Total Comparisons / 3.

Canvas: All 5 Trees with Comparison Costs per Node

Comparisons = Level of Node
Tree Structure Comparisons per Key (10, 20, 30) Total Comparisons Average Comparisons Evaluation
Tree 1: 10 → 20 → 30 10: 1, 20: 2, 30: 3 1 + 2 + 3 = 6 6 / 3 = 2.0 Right Skewed (h = 3)
Tree 2: 10 → 30 (left 20) 10: 1, 30: 2, 20: 3 1 + 2 + 3 = 6 6 / 3 = 2.0 Skewed (h = 3)
Tree 3: 20 → 10 (L), 30 (R) 20: 1, 10: 2, 30: 2 1 + 2 + 2 = 5 5 / 3 = 1.67 < 2.0 ⭐ Height-Balanced (Minimum Height h = 2)
Tree 4: 30 → 20 → 10 30: 1, 20: 2, 10: 3 1 + 2 + 3 = 6 6 / 3 = 2.0 Left Skewed (h = 3)
Tree 5: 30 → 10 (right 20) 30: 1, 10: 2, 20: 3 1 + 2 + 3 = 6 6 / 3 = 2.0 Skewed (h = 3)
💡 Why did Tree 3 give the minimum average comparisons?

Because the height of Tree 3 is minimum (h = 2)! That is why when all keys have equal search frequencies, a height-balanced binary search tree gives the best performance.

Part B: What if Keys Have Unequal Search Frequencies?

Now let us come to the actual problem: Optimal Binary Search Tree. In real applications, all keys will not be searched with the same frequency! Some keys are heavily searched (frequently requested), while others are rarely accessed.

Key 10: freq = 3 Key 20: freq = 2 Key 30: freq = 5 (Highest Frequency!)

Which tree organization will be optimal (minimum total cost)? The search cost is calculated by multiplying each key's frequency by the number of comparisons (its level):
Total Cost = ∑ (Frequency × Level)

Canvas: All 5 Trees with Frequencies & Total Cost Calculations

Cost = ∑ (p × Level)

Detailed Breakdown of Total Weighted Cost:

Tree 1: 10 → 20 → 30 10 (L1): 3 × 1 = 3 20 (L2): 2 × 2 = 4 30 (L3): 5 × 3 = 15 Cost = 3 + 4 + 15 = 22
Tree 2: 10 → 30 → 20 10 (L1): 3 × 1 = 3 30 (L2): 5 × 2 = 10 20 (L3): 2 × 3 = 6 Cost = 3 + 10 + 6 = 19
Tree 3: 20 → 10, 30 (Balanced) 20 (L1): 2 × 1 = 2 10 (L2): 3 × 2 = 6 30 (L2): 5 × 2 = 10 Cost = 2 + 6 + 10 = 18
Tree 4: 30 → 20 → 10 30 (L1): 5 × 1 = 5 20 (L2): 2 × 2 = 4 10 (L3): 3 × 3 = 9 Cost = 5 + 4 + 9 = 18
⭐ Tree 5: 30 → 10 → 20 30 (L1): 5 × 1 = 5 10 (L2): 3 × 2 = 6 20 (L3): 2 × 3 = 6 Cost = 5 + 6 + 6 = 17! (MINIMUM!)
💡 The Core Takeaway of Optimal BST:

You can see that across all 5 trees, Tree 5 has given us the best result with minimum cost = 17!
That is the Optimal Binary Search Tree for these 3 keys. Notice that Tree 5 is NOT height-balanced (its height is 3, whereas Tree 3 has height 2). However, based on the search frequencies, key 30 has the highest frequency (5), so keeping it at the Root (requiring only 1 comparison for the most common search) drastically reduces the total search time!

⇒ A height-balanced BST is NOT necessarily an Optimal BST! The optimal tree depends on the frequencies of the keys.

3. Dynamic Programming Solution: 4 Keys Example

Page 3

Example Problem

We are given 4 keys and their corresponding search frequencies:

Index (i) 1 2 3 4
Key (ki) 10 20 30 40
Frequency (pi) 4 2 6 3
📋

Understanding the DP Table Setup & Why Rows/Columns Run from 0 to 4

We have 4 keys: 10 (Key 1), 20 (Key 2), 30 (Key 3), 40 (Key 4). In Dynamic Programming, each cell C[i][j] will store the minimum search cost for a subtree containing keys from index i + 1 up to j (the range (i, j]).

💡 Why include index 0? (The Empty Subtree)

When we pick a key k as root, we divide keys into a left subtree and a right subtree:

  • If Key 1 is chosen as root, what is its left subtree? It has NO keys! It is empty, represented by range (0, 0) with cost = 0.
  • If Key 4 is chosen as root, what is its right subtree? It has NO keys! It is empty, represented by range (4, 4) with cost = 0.
  • Starting rows and columns from 0 allows every empty subtree to be naturally indexed as C[i][i] = 0 without needing special if-else edge cases!
🎯 The Target Goal: Cell C[0, 4]

• C[0, 1] represents Key 1 only {10}.
• C[0, 2] represents Keys 1 to 2 {10, 20}.
• C[0, 4] represents Keys 1 to 4 {10, 20, 30, 40} — the full BST of all 4 keys!

Cells where i > j (like row 2, col 1) are mathematically invalid (start index cannot exceed end index) and are marked with a dash -.

💡 What Are We Actually Doing? (The Big Picture in Simple Words)

Instead of constructing and evaluating all 14 possible binary search trees for 4 keys, Dynamic Programming solves the problem bottom-up, from smaller subtrees to larger subtrees:

Step 1 Diagonal d = 0 Subtrees of 0 keys (Empty tree → Cost = 0)
Step 2 Diagonal d = 1 Subtrees of 1 key (Single node is root → Cost = freq)
Step 3 Diagonal d = 2 Subtrees of 2 keys (Try both keys as root, pick minimum)
Step 4 Diagonal d = 3 Subtrees of 3 keys (Try all 3 keys as root, reuse Step 2 & 3)
Step 5 Diagonal d = 4 Full tree of all 4 keys (Final answer at C[0,4]!)
The Core Takeaway: The diagonal difference d = j - i represents the number of keys inside the subtree! That is why we compute diagonal-by-diagonal.

Step 3: Diagonal j - i = 2 (Two Keys at a Time)

💡 Why 2 Keys Are Simple: Only 2 BST Structures Are Possible!

For any two sorted keys {A, B} (where A < B), exactly two trees can be formed: either A is Root (B becomes right child) OR B is Root (A becomes left child).
Since the root is at Level 1 (1 comparison) and the child is at Level 2 (2 comparisons): Cost = (Root Freq × 1) + (Child Freq × 2).
Intuition: Whichever key has a higher search frequency should be placed at the root to minimize comparisons!

💡 Why 3 Keys Require Testing 3 Candidate Roots:

For any contiguous range of 3 keys, any one of them can serve as the subtree root:
• Pick First Key as root → Left subtree is empty (cost 0), Right subtree has 2 keys (reusing Step 3!).
• Pick Middle Key as root → Left subtree has 1 key (Step 2!), Right subtree has 1 key (Step 2!).
• Pick Last Key as root → Left subtree has 2 keys (reusing Step 3!), Right subtree is empty (cost 0).
Key Concept: Dynamic Programming doesn't start from scratch—it attaches the already-optimal 1-key and 2-key subtrees below each candidate root and adds the weight W(i, j)!

📐 The Formal Recurrence Relation for OBST

Recurrence Summary
C(i, j) = mini < k ≤ j { C(i, k - 1) + C(k, j) } + W(i, j)
W(i, j) = ∑m = i+1j pm

Meaning of Terms:

  • k is the candidate root chosen from keys i + 1 through j.
  • C(i, k - 1) is the optimal cost of the left subtree.
  • C(k, j) is the optimal cost of the right subtree.
  • W(i, j) is the sum of frequencies of all keys in range (i, j]. Why add this weight? Because when we attach left and right subtrees to root k, every node's depth increases by 1, so each key's comparison count increases by 1 × frequency!
  • Base Cases: C(i, i) = 0 and W(i, i) = 0 for all i.
⏱️ Time Complexity:

• Table size: O(n²) cells.
• For each cell, we try k ranging from 1 to n (takes O(n) time).
• Total Time Complexity = O(n³).
• Note: Can be optimized to O(n²) using Knuth's optimization since R[i, j-1] ≤ R[i, j] ≤ R[i+1, j]!

💾 Space Complexity:

• Cost Table C of size (n+1) × (n+1).
• Root Table R of size (n+1) × (n+1).
• Weight Table W of size (n+1) × (n+1).
• Total Auxiliary Space = O(n²).
