1. Inorder Predecessor & Successor in a BST

Fundamental definitions, BST ordering properties, sub-tree vs ancestor rules, and boundary convergence

Binary Search Trees • Unit 4

💡 Teacher's Desk Memo:

"In a Binary Search Tree (BST), the in-order traversal (Left → Root → Right) naturally visits all keys in strictly ascending sorted order! Because of this invariant, finding the predecessor and successor of a given key X means finding its immediate neighbors in the sorted sequence. A novice uses an array with O(N) space. A master algorithmist navigates directly down the tree in O(H) time using zero extra memory!"

Formal Problem Definition

Given the root of a Binary Search Tree (BST) and a target numerical key X:

⏮️ Inorder Predecessor

The node with the largest value strictly smaller than key X. In the in-order sequence, it is the element located immediately before X.

Predecessor = max { node.val | node.val < X }

⏭️ Inorder Successor

The node with the smallest value strictly greater than key X. In the in-order sequence, it is the element located immediately after X.

Successor = min { node.val | node.val > X }
⚠️ Important Edge Condition:

The target key X does not need to be physically present in the BST! If X is absent, the predecessor is the largest element in the tree smaller than X, and the successor is the smallest element greater than X.

🧭 Structural Invariants: Subtree Extrema vs Ancestor Tracking

The BST ordering property guarantees two distinct search mechanisms depending on whether child subtrees exist:

Rule 1: Children Exist Local Extrema

Subtree Extrema Search

When target node X has child subtrees, the search is purely local within its children:

  • Predecessor: Move to left child, then follow right pointers to the rightmost leaf (maximum element in left subtree).
  • Successor: Move to right child, then follow left pointers to the leftmost leaf (minimum element in right subtree).

Max in Left Subtree = Predecessor • Min in Right Subtree = Successor

Rule 2: Children Missing Ancestor Turns

Ancestor Turn Tracking

When target node X has NO left or right children, search the root-to-leaf path:

  • Predecessor: The deepest ancestor from which we took a RIGHT turn (the closest ancestor smaller than X).
  • Successor: The deepest ancestor from which we took a LEFT turn (the closest ancestor greater than X).

Last Left Turn = Successor • Last Right Turn = Predecessor

Comparison: Brute Force vs Optimal Traversal

💡 The Optimal Algorithm Blueprint: How It Works Without Parent Pointers

The "Candidate Caching" paradigm that solves predecessor & successor in a single pass (O(H) Time, O(1) Memory)

Core Intuition
1️⃣ Turn Left key < curr->data
suc = curr;
curr = curr->left;

🎯 WHY this action? Because curr->data > key, curr is a proven upper bound for key. Moving left searches for a tighter successor (smaller value that still exceeds key).

🛡️ Invariant Maintained: suc caches the closest ancestor strictly greater than key. If left subtree has no values > key, this cached value is guaranteed to be the final answer!

2️⃣ Turn Right key > curr->data
pre = curr;
curr = curr->right;

🎯 WHY this action? Because curr->data < key, curr is a proven lower bound for key. Moving right searches for a tighter predecessor (larger value that is still less than key).

🛡️ Invariant Maintained: pre caches the closest ancestor strictly smaller than key. If right subtree has no values < key, this cached value is guaranteed to be the final answer!

3️⃣ Key Matched key == curr->data
pre = max(left_subtree);
suc = min(right_subtree);

🎯 WHY this action? Subtree elements are numerically closer to curr than any ancestor. Left subtree maximum is the immediate smaller neighbor; right subtree minimum is the immediate larger neighbor.

🛡️ Invariant Maintained: If either child is null, the previously recorded turn ancestors are naturally preserved—zero backtracking needed!

✨ The "Aha!" Moment: Why No Backtracking or Parent Pointers are Needed

Students often wonder: "If a node has no children (like leaf node 45), how can we find its predecessor/successor above it without parent pointers?"
Answer: We already visited those ancestors while walking down from the root! Because we updated pre and suc at every turn on the way down, when we arrive at a childless node, our pointers already contain the exact ancestors we need!

🐢 Approach 1: Brute Force (In-Order Traversal & Array Lookup)

Time O(N) • Space O(N)

We execute a standard recursive in-order traversal (Left → Visit → Right) storing all node values in a dynamic array (`std::vector`).

Array Inspection for Key = 40:

Index of 40 is idx = 4. Predecessor is arr[3] = 35. Successor is arr[5] = 45.

Disadvantage: We had to touch all 11 nodes and allocate memory for the entire tree!

⚡ Approach 2: Optimal BST Traversal (O(H) Time, O(1) Space)

Unlike Brute Force (which dumps the whole tree into a flat array), the Optimal algorithm searches along a single root-to-leaf path. Depending on where the target key sits in the tree, the algorithm resolves using one of the 3 structural cases below:

No Extra Memory • Single Path O(H)
🌳 Case 1: Subtrees Exist

Key is in tree and has child subtrees. Search is local inside children (Subtree Extrema).

🍃 Case 2: Leaf / No Subtrees

Key is in tree but has no children. Look upwards at root-to-leaf ancestor turns.

🔍 Case 3: Absent Key

Key is not in the BST. Search terminates at null; floor and ceil candidates captured.

⚡ Optimal Case 1: Key Found & Has Both Subtrees (Key = 30)

Subtree Extrema Rule
1 At Root Node 50 (Inspect key = 30) Action: Cache suc = 50, Branch Left

🎯 WHY branch left and cache 50? Because 30 < 50, node 50 is strictly greater than the target key, making it a valid candidate for successor. In a BST, all keys smaller than 50 reside strictly in its left subtree. Thus, branching left is the only direction that can yield an even smaller (tighter) successor.

🛡️ Invariant / Edge-case: We cache suc = 50 before leaving node 50. If the left subtree has no values > 30, node 50 remains our guaranteed correct successor!

2 At Node 30 (Exact Key Match: 30 == 30) Action: Subtree Extrema Search Initiated

🎯 WHY shift to subtree rules? BST ordering guarantees that any key in node 30's left subtree is strictly < 30 and numerically closer to 30 than any ancestor. Likewise, any key in node 30's right subtree is strictly > 30 and closer than any ancestor. Local subtree extrema unconditionally override ancestor turn candidates!

3a Predecessor: Left Subtree Maximum (Node 20) Final pre = 20

🎯 WHY max in left subtree? Node 30 has left child 20. We move to 20 and follow right pointers as far as possible. Because node 20 has no right child, 20 is itself the maximum element in the left subtree. Therefore, pre = 20 is the immediate smaller neighbor!

3b Successor: Right Subtree Minimum (Node 40 → 35) Final suc = 35

🎯 WHY min in right subtree? Node 30 has right child 40. We move to 40 and follow left pointers as far as possible: 40 → left is node 35. Since 35 has no left child, 35 is the minimum element in the right subtree. It replaces ancestor 50 because 35 < 50, giving the tightest possible successor suc = 35!

Step Current Node Comparison & Explicit WHY Rationale Candidate pre Candidate suc
1 50 (Root) 30 < 50 ⟹ WHY: 50 is greater than key (candidate suc). Move left to find tighter upper bound. nullptr 50
2 30 (Match!) 30 == 30 ⟹ WHY: Key found! Immediate neighbors in subtrees are closer than any ancestor. nullptr 50
3a 20 (Left child) Follow right pointers ⟹ WHY: Maximum of left subtree is tightest element smaller than 30. 20 (Final) 50
3b 40 → 35 Follow left pointers to 35 ⟹ WHY: Minimum of right subtree is tightest element greater than 30 (35 < 50). 20 (Final) 35 (Final)
Snapshot: Target Node = 30 (Subtrees Traversed)
Key = 30 Pred = 20 Succ = 35 Search Path

⚡ Optimal Case 2: Key Found but Has No Subtrees / Leaf (Key = 45)

Ancestor Turn Tracking
1 At Root 50: Compare 45 < 50 Turn LEFT ⟹ Cache suc = 50

🎯 WHY cache suc = 50? Because 50 > 45, 50 is an upper bound on 45. We cache it in `suc` and branch left into values smaller than 50 to search for tighter candidates.

2 At Node 30: Compare 45 > 30 Turn RIGHT ⟹ Cache pre = 30

🎯 WHY cache pre = 30? Because 30 < 45, 30 is a lower bound on 45. We cache it in `pre` and branch right into values greater than 30 to search for tighter candidates.

3 At Node 40: Compare 45 > 40 Turn RIGHT ⟹ Update pre = 40

🎯 WHY update pre to 40? Because 40 < 45 and 40 > 30. Node 40 is a tighter lower bound than 30! We update `pre = 40` and branch right.

4 At Leaf Node 45 (Match: 45 == 45) Final pre = 40 • Final suc = 50

🎯 WHY do cached ancestor turns become the final answer? Node 45 has no left child (nullptr) and no right child (nullptr). Because it has no subtrees, its predecessor and successor cannot be in its descendants—they must be ancestors! The deepest ancestor from which we turned right was 40 (closest ancestor < 45). The deepest ancestor from which we turned left was 50 (closest ancestor > 45).

🛡️ Edge-case / Elegance: Zero parent pointers and zero upward tree climbing are needed! Our single downward pass already pre-recorded both values!

Step Current Node Comparison & Explicit WHY Rationale Candidate pre Candidate suc
1 50 (Root) 45 < 50 ⟹ WHY: 50 is greater than key. Left turn caches 50 as closest upper ancestor. nullptr 50
2 30 45 > 30 ⟹ WHY: 30 is less than key. Right turn caches 30 as lower ancestor candidate. 30 50
3 40 45 > 40 ⟹ WHY: 40 is less than 45 and tighter than 30 (40 > 30). Updates pre to 40. 40 50
4 45 (Leaf Match!) 45 == 45 ⟹ WHY: Subtrees are null! Last turn ancestors (pre=40, suc=50) naturally complete the answer. 40 (Final) 50 (Final)

⚡ Optimal Case 3: Key is Not Present in the Tree (Key = 65)

Boundary Floor & Ceil
1 At Root 50: Compare 65 > 50 Turn RIGHT ⟹ Cache pre = 50

🎯 WHY cache pre = 50? Because 50 < 65, 50 is a valid floor (lower bound). We branch right to search for larger numbers closer to 65.

2 At Node 70: Compare 65 < 70 Turn LEFT ⟹ Cache suc = 70

🎯 WHY cache suc = 70? Because 70 > 65, 70 is a valid ceiling (upper bound). We branch left to narrow the bounding bracket between 50 and 70.

3 At Node 60: Compare 65 > 60 Turn RIGHT ⟹ Update pre = 60

🎯 WHY update pre to 60? Because 60 < 65 and 60 > 50, node 60 is a much tighter floor than 50! We update `pre = 60` and attempt to move right.

4 Pointer becomes nullptr (Search Exhausted) Final pre = 60 • Final suc = 70

🎯 WHY do cached bounds correctly resolve absent keys? Because 65 does not exist in the BST, the traversal terminates at `nullptr`. However, throughout the walk down, every right turn tightened the lower bound (`pre = 60`) and every left turn tightened the upper bound (`suc = 70`). The final cached pointers form the exact mathematical bounding interval: $[60 < 65 < 70]$!

1 50 (Root) 65 > 50 ⟹ WHY: 50 is less than key. Right turn records 50 as candidate floor. 50 nullptr
2 70 65 < 70 ⟹ WHY: 70 is greater than key. Left turn records 70 as candidate ceil. 50 70
3 60 65 > 60 ⟹ WHY: 60 is less than 65 and tighter than 50 (60 > 50). Updates floor pre = 60. 60 70
4 nullptr Pointer hit null ⟹ WHY: Key is absent. Invariant guarantees pre=60 and suc=70 form the tightest bounding bracket. 60 (Floor) 70 (Ceil)

#include <iostream>

// Definition for a Binary Search Tree Node
struct Node {
    int data;
    Node* left;
    Node* right;
    Node(int val) : data(val), left(nullptr), right(nullptr) {}
};

// Function: findPreSucOptimal
// Finds Inorder Predecessor and Successor of a given key in BST
// Time Complexity: O(H) where H is tree height | Space: O(1)
void findPreSucOptimal(Node* root, Node*& pre, Node*& suc, int key) {
    pre = nullptr;
    suc = nullptr;
    Node* curr = root;

    while (curr != nullptr) {
        if (curr->data == key) {
            // Case 1: Predecessor is maximum element in left subtree
            if (curr->left != nullptr) {
                Node* temp = curr->left;
                while (temp->right != nullptr) {
                    temp = temp->right;
                }
                pre = temp;
            }

            // Case 2: Successor is minimum element in right subtree
            if (curr->right != nullptr) {
                Node* temp = curr->right;
                while (temp->left != nullptr) {
                    temp = temp->left;
                }
                suc = temp;
            }
            return; // Finished searching
        }
        else if (key < curr->data) {
            // curr is greater than key -> candidate for successor!
            suc = curr;
            curr = curr->left; // Search left for tighter successor
        }
        else {
            // curr is smaller than key -> candidate for predecessor!
            pre = curr;
            curr = curr->right; // Search right for tighter predecessor
        }
    }
}

🔍 Step-by-Step Code Dissection: Why This While-Loop Is Complete

1. While Loop Traversal:

We start at root and iteratively walk down one level per iteration. This guarantees O(H) time and O(1) space.

2. Turning Left (key < curr->data):

Since curr->data is larger than key, curr is a valid candidate for successor! We record suc = curr and go left to search for an even smaller (tighter) successor.

3. Turning Right (key > curr->data):

Since curr->data is smaller than key, curr is a valid candidate for predecessor! We record pre = curr and go right to search for an even larger (tighter) predecessor.

4. Exact Match (curr->data == key):

If left child exists, go left then all the way right (max of left subtree). If right child exists, go right then all the way left (min of right subtree). If either child is null, the previously recorded turn ancestors are automatically preserved!

#include <iostream>
#include <vector>

// Helper: Inorder Traversal to collect nodes in sorted order
void inorderTraversal(Node* root, std::vector<Node*>& nodes) {
    if (root == nullptr) return;
    inorderTraversal(root->left, nodes);
    nodes.push_back(root);
    inorderTraversal(root->right, nodes);
}

// Brute Force: Scan sorted vector (O(N) Time, O(N) Space)
void findPreSucBrute(Node* root, Node*& pre, Node*& suc, int key) {
    pre = nullptr;
    suc = nullptr;
    std::vector<Node*> nodes;
    inorderTraversal(root, nodes);

    int n = nodes.size();
    for (int i = 0; i < n; ++i) {
        if (nodes[i]->data == key) {
            if (i > 0) pre = nodes[i - 1];
            if (i < n - 1) suc = nodes[i + 1];
            return;
        } else if (nodes[i]->data > key) {
            // For absent keys: first element greater is successor
            suc = nodes[i];
            if (i > 0) pre = nodes[i - 1];
            return;
        }
    }
    // Key is larger than all elements in BST
    if (n > 0) pre = nodes.back();
}

Formal Asymptotic Complexity Breakdown

🐢 Brute Force Complexity

  • Time Complexity: O(N). Inorder traversal visits every single node in the tree regardless of tree balance or key position.
  • Auxiliary Space: O(N). Allocates memory for an array/vector of size N, plus O(H) recursion stack frames.

⚡ Optimal BST Traversal Complexity

  • Time Complexity: O(H) where H is the height of the BST.
    • Balanced BST (AVL / Red-Black): H = ⌊log₂ N⌋ ⟹ O(log N).
    • Worst Case (Degenerate Skewed Tree): H = N ⟹ O(N).
  • Auxiliary Space: O(1). Uses only two pointer references (`pre` and `suc`) in an iterative while-loop.
Algorithm Balanced BST Time Worst Case Time Auxiliary Space Modifies Tree?
Brute Force (Array) O(N) O(N) O(N) No
Optimal BST Traversal O(log N) O(N) (skewed) O(1) No
