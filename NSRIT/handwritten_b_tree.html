1. Core B-Tree Rules & Definitions

A B-Tree of order m is a multi-way, self-balancing search tree designed to optimize read and write operations on secondary memory disks.

📌 Exact Mathematical Capacity Formulas:

Child Pointer Limits:
  • Max Children = m
  • Min Children (internal) = ⌈m / 2⌉
  • Root Min Children = 2 (if non-leaf)
Key Capacity Limits:
  • Max Keys per node = m - 1
  • Min Keys per node = ⌈m / 2⌉ - 1
  • Root Min Keys = 1

⭐ Important: Every single leaf node in a B-Tree must exist on the EXACT same level (Perfect Height Balance).

2. Comparison Table Across Orders

Order (m) Max Keys (m - 1) Min Keys (⌈m/2⌉ - 1) Max Children (m) Min Children (⌈m/2⌉)
Order 3 (2-3 Tree) 2 keys 1 key 3 children 2 children
Order 4 (2-3-4 Tree) 3 keys 1 key 4 children 2 children
Order 5 4 keys 2 keys 5 children 3 children

3. Summary of Core Operations

Insertion Operation Flow:
  1. Traverse down to find the correct leaf node.
  2. Insert key in sorted order.
  3. If keys > m - 1 (Overflow), find the Median Key.
  4. Promote median key up to parent. Split remaining keys into left & right children.
Deletion Operation Flow:
  1. Locate key in leaf or internal node.
  2. If internal, swap with Inorder Predecessor/Successor.
  3. Delete from leaf node.
  4. If keys < Min Keys (Underflow), Borrow from rich sibling OR Merge with sibling + parent key.

B. Order-5 B-Tree (Max Keys = 4) Key Rule Steps

Max Keys per node = 4 | Min Keys per non-root node = 2 (⌈5/2⌉ - 1)

  • Step 1 to 4: Keys 1, 2, 3, 4 fit inside a single node: `[ 1 | 2 | 3 | 4 ]`. No split required.
  • Step 5: Inserting 5 creates overflow `[ 1 | 2 | 3 | 4 | 5 ]`. Median key is '3'.
  • '3' moves UP to root, leaving left child `[1 | 2]` and right child `[4 | 5]`. (Both children have exactly 2 keys, fulfilling min key rule!).

6. Exhaustive Deletion Dry-Run (Initial Setup & Rules)

Page: 04

Deleting a key from a B-Tree must preserve all fundamental rules: ascending order, min key bounds, and perfect leaf height.

📌 Exact Order-5 Deletion Bounds:

  • Order m = 5: Min Keys per non-root node = ⌈5/2⌉ - 1 = 2 keys. Max Keys = 4 keys.
  • If a node has ≥ 3 keys, deleting a key is direct and immediate (no underflow).
  • If a node has 2 keys (Minimum), removing a key leaves 1 key (UNDERFLOW!). Rebalancing is required via Borrowing (Rotation) or Merging.

2. Internal / Root Node Deletion:
  • Case 2: Replace key with Inorder Predecessor (max in left subtree) or Inorder Successor (min in right subtree).
  • Then recursively delete predecessor/successor key from the leaf node.

7. Deep Dive: Real-World System Applications

Page: 07

Understanding why and where B-Trees and AVL Trees are deployed in modern software architecture is essential for computer science and database system design.

A. B-Tree & B+ Tree Applications (Secondary Storage / Disks)

💡 Core Hardware Reason for B-Trees in Disk Storage:

Disks read and write data in fixed-size blocks (pages), typically 4 KB to 16 KB. A Binary Search Tree requires 1 disk seek per node access (extremely slow due to mechanical/bus latency). A B-Tree node matches disk page size exactly—storing hundreds of keys per node—enabling high fan-out and reducing total tree height to just 3 or 4 levels for millions of records!

1. Database Indexing Engines

• MySQL (InnoDB Storage Engine): Uses B+ Tree indexes for primary keys (clustered index) and secondary keys.
• PostgreSQL & SQLite: Implement B-Tree indexes as the default index type for fast SELECT queries.
• Oracle DB & MS SQL Server: Rely on multi-level B-Trees to handle multi-terabyte table indexing.

2. File System Storage & Extent Mapping

• NTFS (Windows): Uses B-Trees in the Master File Table (MFT) for fast file directory lookups.
• ext4 & Btrfs (Linux): Uses extent trees (B-Tree variant) to track physical disk blocks assigned to large files.
• APFS & HFS+ (Apple macOS/iOS): Uses B-Trees for catalog files and path metadata.

3. Operating System Virtual Memory

• Virtual Memory Page Tables: OS kernels use multi-level tree structures inspired by B-Trees to map virtual memory addresses to physical RAM frames.
• Disk Block Allocators: Efficiently manage free and occupied contiguous disk blocks.

4. Networking, Routers & DNS

• Router IP Lookup Tables: High-speed edge routers index CIDR IP address prefix masks using multi-way trees for sub-millisecond packet routing.
• DNS Servers: Domain name resolution caches use B-Tree lookups for rapid URL-to-IP resolution.

B. AVL Tree Applications (Strict In-Memory Balance)

💡 Core Hardware Reason for AVL Trees in RAM:

In RAM (Main Memory), pointer dereferencing is fast, but depth matters. AVL Trees enforce strict height balancing (Height Difference $\le 1$), guaranteeing worst-case search time of 1.44 log₂ N. They are superior when read operations (searches) far outnumber write operations (insertions/deletions).

1. In-Memory Dictionaries & Sets

• Used in standard programming language runtime libraries to implement fast associative containers (e.g., in-memory key-value maps, ordered sets).

2. Real-Time Games & Physics Engines

• Spatial Indexing & Hitboxes: Tracks 2D/3D active game entities and collision bounding volumes where rendering frame rates demand strict upper-bound lookup guarantees.

3. Compiler Symbol Tables

• Compilers use AVL Trees during semantic analysis to track nested variable scopes, type signatures, and function declarations with predictable performance.

4. Read-Heavy In-Memory Caches

• Preferred in memory-resident cache systems where items are populated once and searched millions of times per second without performance jitter.
