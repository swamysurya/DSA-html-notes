Disk Structure & Hardware Mechanics

Page 1

To understand why database indexing and trees are required, we must look at how data is stored physically on the hard disk. A physical hard disk is structured like a platter that spins on a central spindle.

Core Hardware Terms:

  • Tracks: Concentric logical circles on a platter. They are numbered Track 0, Track 1, Track 2, etc.
  • Sectors: Logical wedge-shaped slices that partition the disk.
  • Blocks: The intersection of a Track and a Sector. A block is the smallest unit of read/write transfer between the disk and memory.
  • Block Size: Typically assumed to be 512 bytes for standard database design, but can be larger (e.g., 4KB).
  • Offsets: The address of an individual byte inside a block, starting at 0 and ending at 511.
Interactive Platter Diagram (Hover to inspect): Hover over sectors/tracks to read block coordinates.

Block Addressing Formula:

Any byte on the physical disk is uniquely addressable using three components:

Byte Address = [Track Number] + [Sector Number] + [Byte Offset]

* Note: Hardware reads are always block-level. Even if you want to read just 1 byte at a specific offset, the entire 512-byte block must be loaded into main memory (RAM).

RAM (Main Memory) vs. Hard Disk (Secondary Storage):

A database program cannot access records directly from the disk. When a query is run, the relevant blocks must be brought from secondary storage into main memory (RAM) where the CPU can process them. If changes are made, the memory buffer must be flushed/written back to the disk blocks.

💡 Concept Definition: Organizing data inside the Main Memory (RAM) for active program execution is the study of Data Structures. Organizing data on the disk efficiently to minimize disk block accesses is the study of Database Management Systems (DBMS).

Database Indexing & Block access Math

Page 2

Let us analyze why we need indexing and how much search time is reduced by calculating the exact number of block accesses.

Example Scenario (Without Indexing):

  • Database Table: Employee Table with 100 rows (records).
  • Record Size: Each row takes 128 bytes (Employee ID = 10B, Name = 50B, Dept = 10B, etc.).
  • Block Size: 512 bytes.

Calculations:

  1. Records per Block: 512 bytes / 128 bytes = 4 records/block.
  2. Total Blocks Needed: 100 records / 4 records per block = 25 blocks.
  3. Access Time: Searching for a random record (e.g. employee ID = 42) requires sequentially scanning the table block-by-block. At worst, you must access all 25 blocks.
Block Partitioning: Records (128B) vs. Index Entries (16B)

Example Scenario (With Indexing):

We create a Dense Index. Each index entry contains: Employee ID (Key = 10B) + Record Pointer (Pointer = 6B) = 16 bytes.

Calculations:

  1. Index Entries per Block: 512 bytes / 16 bytes = 32 entries/block.
  2. Total Index Blocks Needed: 100 entries / 32 entries per block = 4 blocks (3.125 blocks, rounded up).
  3. Access Time: To search for a record, we read the index blocks. Since the index fits in 4 blocks, we read at most 4 blocks to find the index entry, retrieve the record pointer, and then perform 1 block access to retrieve the actual row.
  4. Total Blocks Accessed: 4 Index Blocks + 1 Data Block = 5 block accesses (compared to 25 accesses without indexing!).

Multi-Level Indexing & Index Scaling

Page 3

As databases scale, index files grow. For example, if a table has 10,000 records, the dense index file would require:

10,000 / 32 = 313 index blocks!

Searching through 313 index blocks sequentially is slow. To solve this, we build a **Multi-Level Index** (adding a higher-level sparse index on top of the first-level index).

Sparse High-Level Indexing Rules:

Instead of creating an entry for every single row, a higher-level index contains only one entry per *block* of the lower-level index.

  • Level 1 Index (Dense): Has 10,000 entries (takes 313 blocks).
  • Level 2 Index (Sparse): Stores the starting key value of each of the 313 blocks. It only needs 313 entries.
  • Level 2 Blocks: 313 entries / 32 entries per block = 10 blocks.
  • Level 3 Index (Sparse): Stores the starting key of each of the 10 blocks (10 entries). It easily fits in 1 block!

Total Block Accesses for search:

1 (Level 3 Block) + 1 (Level 2 Block) + 1 (Level 1 Block) + 1 (Data Block) = 4 Block Accesses total!

Self-Managing Hierarchical Trees:

Manually updating multi-level indices when records are inserted or deleted is highly complex. If database size increases, we must automatically add index levels. If records are deleted, we should reduce them.

💡 **The Goal:** We need a **self-managing, self-balancing multi-level indexing structure** that automatically handles insertions, deletions, block splitting, and merges dynamically. This directly leads to the invention of B-Trees and B+ Trees!

M-Way Search Trees & Index Nodes

Page 4

Before studying B-Trees, we look at their predecessor: the **M-Way Search Tree**. While a Binary Search Tree (BST) allows only 1 key and at most 2 children per node, an M-Way tree allows multiple keys and children.

M-Way Search Tree Rules:

  • Each node has at most M children.
  • Each node contains at most M - 1 sorted keys.
  • Subtrees are split by key bounds:
    • Left child contains keys $< K_1$.
    • Middle child contains keys between $K_1$ and $K_2$.
    • Right child contains keys $> K_2$.
  • M is the degree of the tree.
Structure of a 4-Way Node (3 Keys + 4 Child Pointers):

The Unbalanced Height Problem:

In standard M-Way search trees, there is **no rule** stating how full a node must be. If keys are inserted sequentially (e.g. 10, 20, 30, 40), we can end up creating long linear chains of nodes with single keys, resulting in a height of $H = N$. This defeats the purpose of indexing and degrades performance back to linear search.

🚨 Solution: We must impose strict height-balancing and node-filling rules. A B-Tree is simply an M-Way Search Tree governed by balancing rules.

B-Trees vs. B+ Trees

Page 5

Defining Rules of B-Trees:

  1. Minimum Children: Every node (except the root) must contain at least ⌈M/2⌉ child pointers. This ensures the tree is always at least half-full.
  2. Root Node: The root must have at least 2 children (unless it is a leaf).
  3. Leaf Uniformity: All leaf nodes must be at the exact same depth level.
  4. Bottom-Up Growth: Unlike BSTs, B-Trees grow from the bottom up. When a node overflows ($keys > M-1$), it splits, and the median key is pushed up to the parent.

Key Differences: B-Tree vs B+ Tree

Feature B-Tree B+ Tree
Record Pointers Stored at all levels next to keys. Stored **only** in leaf nodes.
Key Duplication All keys are unique. Inner keys are duplicated in leaves.
Leaf Linking Leaf nodes are independent. Leaves are linked like a Linked List.
Index Type Mixed index model. Dense leaves, sparse inner levels.
